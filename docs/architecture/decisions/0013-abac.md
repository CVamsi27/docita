# 0013: Layered attribute-based access control on top of RBAC (ABAC-on-RBAC)

- **Status**: accepted
- **Date**: 2026-08-06
- **Deciders**: platform
- **Tags**: auth, security, compliance

## Context

The object-level access inventory in [`ABAC_MIGRATION_PLAN.md`](../../analysis/ABAC_MIGRATION_PLAN.md) found that the API's only object-level gates are the roles matrix (`@Roles` + `getDbRolesForTarget`), the tier/feature gates (`@RequireFeature`, `TierGuard`), tenant scoping inside repository queries, and RLS as the data-plane backstop. Attribute-based conditions are partially implemented but not enforced:

- `AuthorizationService` (with `ResourcePolicyRegistry` and the four legacy `ResourcePolicy` implementations in `apps/api/src/shared/modules/authorization/`) exists but is **unwired** — no guard invokes it. *(Superseded 2026-08-07: the legacy programmatic engine was removed — see the Phase D completion note in Consequences; the path is now the single-engine `AuthorizationModule`.)*
- `@DoctorPatientScoped` / `PatientDoctorGuard` is registered in `AuthModule` but **not applied to any live controller route**. Doctor-assignment pinning and PATIENT own-row enforcement exist nowhere on the route surface.
- PATIENT self-service reads (`/patient-portal/*`) are gated by `@Roles(Role.PATIENT)` at the controller level; the patient profile is derived from the JWT, not from a per-request resource policy.

The route surface therefore cannot express "object belongs to your clinic **and** you are assigned / you own the row" without a policy stage. Adding more `@Roles` entries does not scale (role explosion) and cannot encode resource attributes (owner, classification, consent state).

## Decision

Ship a **layered ABAC-on-RBAC** model where the existing guard chain stays in force and a new policy stage adds object-level conditions only:

1. **Guard order** (unchanged, then additive): JWT → tenant/context → roles matrix → subscription → tier/feature → **new `PolicyGuard`** (global `APP_GUARD`, no-op without metadata) → service/repository tenant scoping → RLS.
2. **Deny-overrides + default-deny.** The `PolicyGuard` denies (403, or 404 for `tenant_mismatch` to preserve the no-existence-disclosure wire contract) on anything but an explicit allow. A declared policy with no registered resolver is a misconfiguration and denies — never passes.
3. **Typed-policy engine in a new workspace package** `packages/authorization`: pure, framework-agnostic `AbacPolicy` implementations (`evaluatePolicy`, `denyOverrides`, builders) with no NestJS or Prisma imports. The API's `AuthorizationAction`/`AuthorizationDenyReason` become type aliases of the package vocabulary, keeping the outward contract stable.
4. **Zod-first attributes.** Subject/resource/environment attribute schemas live once in `packages/types/src/authorization/` and are the single source of truth; no parallel hand-written interfaces.
5. **Decorator-driven posture.** Routes declare `@RequirePolicy(resource, action)`; a static gate (`check:policy-resolver-coverage`, wired into `verify:standard`) fails the build if a declared resource has no registered resolver.
6. **No XACML.** Policies are typed TypeScript classes, not XML/JSON policy documents — the policy set is small and reviewed in PRs.
7. **UI remains non-authoritative.** A frontend permission snapshot (Phase C7 of the migration plan) is deferred to a later slice.
8. **RLS stays on** as the data-plane backstop; ABAC is defense-in-depth at the application layer, not a replacement.

## Assignment-pinning: ENABLED on the staff surface 2026-08-06 (C1 phase-2)

**Status: ENABLED on the staff surface (2026-08-06, C1 phase-2).** `PatientResourceResolver` now returns `requiresAssignment: true` for the staff `GET/PATCH /patients/:id` surface. The differential-equivalence pass (package oracle tests + e2e) proves the new semantics equal the legacy `PatientDoctorGuard` *intended* semantics: only plain `DOCTOR` is pinned; `ADMIN_DOCTOR`/`NURSE`/`RECEPTIONIST`/`ADMIN`/`INTERNAL` bypass (mirroring the legacy guard's bypass list); PATIENT own-row unchanged; cross-clinic still 404.

Existing-user compatibility: `packages/db/scripts/backfill-patient-doctor.ts` creates active `PatientDoctor` rows from appointment history **before** the flag flipped, so no existing doctor-patient relationship lost access. This is a deploy-order tripwire — the backfill must run against the target database before the flip ships (see the resolver's file doc).

Emergency escape hatch: `PolicyGuard` honors `x-break-the-glass` on `@EmergencyAccess()` routes (added to `GET /patients/:id`); `BreakTheGlassInterceptor` audits `EMERGENCY_ACCESS_GRANTED` and sets the RLS bypass. **Emergency access is read-only** (`@EmergencyAccess()` on `findOne` only — an unassigned doctor cannot emergency-update a patient; writes are deliberately more sensitive, and the interceptor would audit an update identically if decorated later). BTG deliberately bypasses the `tenant_mismatch` → 404 mapping (cross-clinic BTG reads return 200, audited and reason-gated) because it also bypasses RLS.

The future patient-portal resolver continues to flip the same `requiresAssignment` flag for portal reads.

### Earlier deferral (superseded by the above)

Originally (first slice, 2026-08-06) the staff resolver kept `requiresAssignment` `false` because assignment-pinning was not enforced anywhere on the live staff surface and enforcing it silently would have tightened clinician access without a product decision. That deferral is now superseded: the product decision landed with the differential-equivalence pass, the backfill, and the emergency escape hatch.

## Appointments surface: ENABLED 2026-08-07 (C2)

**Status: ENABLED (2026-08-07, C2).** `GET/PATCH /appointments/:id` and `PATCH /appointments/:id/cancel|reschedule` now declare `@RequirePolicy('appointment', 'read'|'update')` and are enforced by `AppointmentAbacPolicy` (`packages/authorization`) via the global `PolicyGuard`, with attributes resolved by `AppointmentResourceResolver`. The slice is **mirror-only**: every evaluated case produces the same wire outcome as before (assigned DOCTOR 200, doctor-mismatch 403, cross-clinic/missing 404 without existence disclosure, other staff clinic-wide 200), proven by the differential-oracle table in the package tests and the `appointment-abac.e2e-spec` (11 cases). The only visible change is the deny message on doctor-mismatch: the deny now fires at the guard stage with the generic `Access denied.` instead of the service-layer message (status unchanged). Assignment is derived from the appointment row's own `doctorId` — no backfill was needed (unlike C1 patients).

**Write-lock deferral (C2.1):** the C2 migration-plan spec also listed "no-show/completed write locks by status attribute". That is **DEFERRED** pending a recorded product decision: no service-layer guard rejects updates to completed/no-show appointments today, so enforcing one at the policy stage would tighten staff (NURSE/ADMIN) behavior beyond the legacy `AppointmentPolicy`. The `status` attribute ships in `resourceAttributesSchema` now (the resolver populates it), so the later branch is a one-line policy change behind the decision. The oracle row and the e2e case `NURSE updates a COMPLETED appointment (200)` pin the current baseline — they must flip in the same commit that enables the lock.

## Prescriptions surface: ENABLED 2026-08-07 (C3)

**Status: ENABLED (2026-08-07, C3).** `GET /prescriptions/:id` and both PDF routes (`/pdf/status`, `/pdf`) declare `@RequirePolicy('prescription', 'read')`, and `POST /whatsapp/approve-prescription/:id` declares `@RequirePolicy('prescription', 'update')`, all enforced by `PrescriptionAbacPolicy` (`packages/authorization`) via the global `PolicyGuard`, with attributes resolved by `PrescriptionResourceResolver`. The policy mirrors the legacy `PrescriptionPolicy`: PATIENT own-row read-only (`assignedPatientId === subject.patientId`, parity for the future portal surface); **read retains the matrix roles** — a non-author DOCTOR may read any clinic prescription; DOCTOR author-of-record on `update`/`delete` (`assignedDoctorIds` derived from the row's own `doctorId`); `ADMIN_DOCTOR`/`NURSE`/`RECEPTIONIST`/`ADMIN`/`LAB` clinic-wide; default-deny. The `status` attribute carries `approvalStatus` (populated, not enforced — no approval-state write lock today, same C2.1 posture). The resolver falls back from the nullable `Prescription.clinicId` (`onDelete: SetNull`) to the required `appointment` relation's `clinicId`.

**Author-of-record on approve is a recorded tightening (C3.1).** Today `POST /whatsapp/approve-prescription/:id` is roles-only (`@Roles(DOCTOR, ADMIN, ADMIN_DOCTOR)`) — any DOCTOR in the clinic can approve any prescription, and the service sets `approvedById` without an ownership check. Enforcing `update` author-of-record changes that: a plain DOCTOR must be the author (`prescription.doctorId === user.id`) or the guard 403s before the handler; `ADMIN`/`ADMIN_DOCTOR` remain clinic-wide per the legacy policy. This is the same precedent as C1 assignment-pinning — the differential oracle encodes the intended semantics and the `prescription-abac.e2e-spec` pins the new wire behavior (non-author DOCTOR approve 403, author/ADMIN/ADMIN_DOCTOR 201). **`approve-invoice` in the same controller stays roles-only (C4 scope)** — recorded so the asymmetry reads as a decision, not an oversight, and the same question will recur for invoices.

Read-side equivalence: cross-clinic/missing prescriptions 404 without existence disclosure (resolver 404s missing rows; the policy's tenant discipline maps cross-clinic to 404 via the guard), matching the clinic-scoped `findOne`. The existing `prescriptions.e2e-spec` (8 tests) passes unchanged; the new `prescription-abac.e2e-spec` adds 11 cases.

## Invoices & lab orders surface: ENABLED 2026-08-07 (C4)

**Status: ENABLED (2026-08-07, C4).** The invoice object routes (`GET/PATCH /invoices/:id`, `payment-activity`, `claim-readiness`, `submit-claim`, both PDF routes) declare `@RequirePolicy('invoice', 'read'|'update')`, `POST /whatsapp/approve-invoice/:id` declares `@RequirePolicy('invoice', 'update')`, and the lab-order object routes (`GET /clinical/lab-tests/orders/:id`, `PUT .../status`, and the workflow sample/result/payment/release routes) declare `@RequirePolicy('lab-order', 'read'|'update')` — enforced by `InvoiceAbacPolicy` and `LabOrderAbacPolicy` (`packages/authorization`) via the global `PolicyGuard`, with attributes resolved by `InvoiceResourceResolver` and `LabOrderResourceResolver`. Both mirror the legacy contract: PATIENT own-row (`assignedPatientId === subject.patientId`, portal parity), clinical staff clinic-wide after the matrix gates (incl. LAB on lab orders), tenant discipline → cross-clinic 404. The invoice resolver falls back from the nullable `Invoice.clinicId` to the required `patient` relation's `clinicId`; the lab-order resolver carries `ownerId` = `orderedBy` (populated, not enforced).

**C4.3 — approve-invoice stays clinic-wide (resolves C3.1).** Unlike `approve-prescription` (author-pinned in C3), `approve-invoice` is NOT author-pinned: the legacy `InvoicePolicy` has no doctor author-of-record branch, so any clinic DOCTOR/ADMIN/ADMIN_DOCTOR may approve any clinic invoice. The policy adds tenant discipline only. The e2e pins this (non-author DOCTOR approve 201, ADMIN approve 201).

**C4.1 — lab-order assignment pinning + payment-state conditions DEFERRED.** The C4 migration-plan spec listed "fulfilment roles + lab-order assignment + front-desk payment attribute". Fulfilment roles are already matrix-encoded (`API_LAB_WORKSPACE` incl. LAB) and the front-desk payment attribute is matrix-encoded too (`API_LAB_PAYMENT_VERIFICATION` = ADMIN/ADMIN_DOCTOR/RECEPTIONIST — the policy stage never sees LAB on that route). Lab-order **assignment pinning** (LAB → `LabTestOrder.labId`) and payment-state write conditions are **DEFERRED**: no service-layer guard exists today (labId scoping exists only on the list queue; object routes check clinic only), so enforcing them would tighten LAB/staff behavior beyond the legacy contract. The `status` attribute carries `LabTestOrderStatus` (populated, not enforced); the oracle rows + e2e pin the baseline (LAB acts on any clinic order; RECEPTIONIST verifies payment) and must flip in the same commit as the decision.

## Audit logs surface: ENABLED 2026-08-07 (C5)

**Status: ENABLED (2026-08-07, C5).** Both audit routes — `GET /audit-logs` (`AuditController`, `AuditLogsApiAccess` = ADMIN + INTERNAL) and `GET /audit/recent` (`AuditSummaryController`, `AuditSummaryApiAccess` = ADMIN + ADMIN_DOCTOR + DOCTOR) — declare `@RequirePolicy('audit-log', 'read')`, enforced by `AuditLogAbacPolicy` (`packages/authorization`) via the global `PolicyGuard`. Decision ordering: INTERNAL bypass (cross-clinic read is the INTERNAL job — the controller skips the clinic filter for INTERNAL) → not-applicable → tenant discipline (cross-clinic → 404 mapping) → audit-reader role matrix (union of the two controllers' gates: ADMIN/ADMIN_DOCTOR/DOCTOR) → default-deny (no PATIENT own-row — the audit surface is staff-only).

**Differential-equivalence.** The policy role set is the union of the two role gates, but it can never widen the wire contract because `RolesGuard` runs before `PolicyGuard` in the global guard order (`app.module.ts`): on `/audit-logs`, ADMIN_DOCTOR/DOCTOR are rejected by the roles gate before the policy; on `/audit/recent`, INTERNAL is rejected by the roles gate. The resolver (`AuditLogResourceResolver`) is scope-based — the list routes carry no `:id`, and the controller already forces `filter.clinicId` to the requester's clinic — so the resource clinicId IS the requester's own tenant and `tenant_mismatch` never fires on today's routes; it pins the no-existence-disclosure invariant for any future `:id` route. Cross-clinic targeting via `?clinicId=` is additionally rejected by `TenantGuard` (`CLINIC_SCOPE_MISMATCH`, 403) before any other stage — pinned in the e2e.

**VIEW_PROFILE obligations.** The C5 migration-plan spec listed "VIEW_PROFILE read obligations". Those are enforced at the controller layer today: `logPatientPhiRead(..., 'VIEW_PROFILE')` audits PHI-profile reads at the call site (the C1 precedent, pinned by `patient-phi-read-audit.e2e-spec.ts`). The policy-emitted obligation adapter (B5) remains deferred to Phase D2 — this slice ships the tenant-scoped-read posture, not new logging paths.

**No guard weakened.** `@Roles`, `@RequireFeature(Feature.AUDIT_LOGS)`, `TierGuard`, the controller's forced-filter, and `TenantGuard` all stay in force. The e2e also fixed a stale pre-existing failure in `patient-phi-read-audit.e2e-spec.ts` (its doctor patient-read helper predated C1 phase-2 assignment pinning and never created a `PatientDoctor` row).

## Referral-partner cross-tenant access: DEFERRED / BLOCKED (C6 decision, 2026-08-07)

**Status: BLOCKED (2026-08-07, C6) — recorded decision, no code.** The C6 migration-plan spec ("cross-tenant `accessScope` support for program partner accounts") is **deferred** because the referral/partner program itself is **BLOCKED** per `EXECUTION_PLAN.md` (external prerequisite: partner signup, facility-lead intake, internal progression, the approved 10% first-year policy, clinic discount policy, anti-abuse controls, and notification/calendar handoff must all have implementation + test evidence before the program is live). Enforcing an ABAC policy for a cross-tenant `referral` resource would be speculative: there is no cross-tenant wire contract today to mirror, and every current referral surface (`partner-portal`, `clinic-referral`, `internal-referral`, `public-booking`) is single-tenant — tenant discipline as it exists (one `clinicId` per subject/resource) already covers them.

**When the program unblocks:** the engine is already shaped for it — `SubjectAttributes`/`ResourceAttributes` in `packages/types/authorization` are the extension point (an `accessScope: 'clinic' | 'partner' | ...` attribute, or a multi-clinic collection, is an additive schema field), and a new `referral` policy + resolver would follow the C2–C5 mirror pattern. Until then `referral` is intentionally **not** registered in either ABAC registry, so any premature `@RequirePolicy('referral', ...)` route fails closed (`policy_not_found` → deny) — the safe default. The `policy_not_found` unit test uses a deliberately off-map resource name (`not-a-resource`) so it never needs repointing when `referral` eventually ships.

## Frontend permission snapshot: ENABLED 2026-08-07 (C7)

**Status: ENABLED (2026-08-07, C7).** `GET /auth/effective-permissions` returns a server-derived permission snapshot for the authenticated staff user: `role`, `tier`, `planMode`, `hasIntelligence`, the user's `permissions`, and a per-target `read`/`write` map over every `APP_ACCESS_MATRIX` target. The computation is a **pure, tested mirror** — `computeEffectivePermissions` in `@workspace/utils` — that replicates the client `canAccessTarget` decision order exactly (comingSoon → Front Desk mode block → roles → permissions → feature via `hasFeatureAccess` → tier via `TIER_SENTINEL_FEATURES`, which moved to `packages/types/access` as the SSOT shared by both the client fallback and the server). INTERNAL snapshots have every target true (the admin-console bypass — the internal app is INTERNAL-role gated and consumes the same endpoint semantics).

**NON-authoritative by contract.** The snapshot only previews decisions for the UI; the server remains the enforcement point (ACCESS_AUDIT non-negotiable 2 — the RBAC/tier/policy guard chain is untouched). The client fetches it once per session via `useEffectivePermissions` and `canAccessTarget` prefers the snapshot entry when present, falling back to the local matrix otherwise — the documented offline fallback; the module cache is cleared on logout so a second user in the same tab never inherits a stale snapshot. Existing call sites (inbox tabs, consultation after-visit strip) behave identically when the snapshot is absent (default path unchanged), so the slice ships with **no UI regression**. The route is gated to staff + INTERNAL roles (incl. LAB, which has matrix targets) — portal roles excluded (the matrix targets are staff/console surfaces); no `TierGuard`/`RequireFeature` because the payload itself mirrors tier-blocked targets (false) — gating the endpoint would hide the denial information the UI needs.

**Known mirror divergence (recorded).** The mirror is decision-order-identical to the client fallback, with one bounded divergence: the client's `canAccessFeature` also honors app-local AI feature flags (`AI_FEATURES_ENABLED` / `AI_GATED_FEATURES` in the permission store) that the server-side `hasFeatureAccess` does not model. For AI-gated targets the snapshot can say accessible while the offline fallback would say not. No currently-wired snapshot call site gates an AI-flagged target (`PAGE_CODING_QUEUE` + inbox tabs), so the divergence is latent; when an AI-gated target is wired to the snapshot, either exclude it from the snapshot or mirror the flags. The client permission check wraps `parseAppPermission` while the mirror checks raw `APP_PERMISSIONS_BY_ROLE` membership — equivalent for the known-permission set (parse is identity-or-null for matrix permissions).

## Alternatives considered

| Option | Pros | Cons | Why rejected |
| --- | --- | --- | --- |
| Extend the roles matrix only | No new machinery | Role explosion; cannot encode resource attributes (owner, classification, consent) | Does not satisfy the inventory requirements |
| Wire the legacy `AuthorizationService.can()` directly | Reuses existing code | Legacy policies are Nest-bound, not reusable by the worker/frontend snapshots; no attribute schemas | The package promotion satisfies the two-consumer rule and keeps policies pure |
| XACML/policy documents | Standards-driven | Heavyweight, stringly-typed, poor DX for a small policy set | Typed classes reviewed in PRs are simpler (KISS) |
| Enforce assignment-pinning now | Closes the gap immediately | Unauthorized behavior tightening on the staff surface | Requires a product decision + differential pass first |

## Consequences

- Positive: object-level conditions become expressible (`tenant + owner/assignment + classification`), the engine is reusable by the worker and future frontend snapshots, deny reasons are machine-readable, and the static gate catches resolver misconfigurations at CI time.
- Negative: a second enforcement stage adds surface area; every new `@RequirePolicy` route must register a resolver or the guard 403s (intended, fail-closed); attribute vocabulary must be versioned in `packages/types`.
- Follow-up work: C2.1 (write-lock product decision), C2.2 (clinical/consultation/appointment-request/doctor-delay controllers), C6 cross-tenant referral (**recorded decision 2026-08-07: DEFERRED / BLOCKED on the partner-program release** — no code shipped; see the C6 section), Phase D retirement ledger, Phase E parity-gate cutover, worker-side consumption of `@workspace/authorization`. The C3.1 `approve-invoice` question is **closed** (C4.3: stays clinic-wide); C5 audit-log resources and C7 frontend permission snapshot are **shipped (2026-08-07)**; the VIEW_PROFILE obligation adapter (B5) is deferred to Phase D2.

  **Phase D completion (2026-08-07):** the legacy *programmatic* engine inside
  `AuthorizationService` — `ResourcePolicyRegistry`, the five `ResourcePolicy`
  implementations in `authorization/policies/`, and the `can()`/`check()`
  methods — was **REMOVED**. It was unwired: the only consumer of the service,
  `PolicyGuard`, calls `evaluateAbac` (this decision's engine) exclusively, and
  the legacy `can()` path had zero production callers. The removal weakens no
  guard (see the supersede note in [`ABAC_RETIREMENT_LEDGER.md`](../../analysis/ABAC_RETIREMENT_LEDGER.md));
  the pure engine + differential oracles + ABAC e2e suites are the surviving
  semantic reference. The engine stays additive and the guard chain
  (JWT → tenant → roles → subscription → tier/feature → PolicyGuard) is
  unchanged.
