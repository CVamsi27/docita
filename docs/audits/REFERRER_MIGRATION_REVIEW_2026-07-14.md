## Schema-lock compliance

The migration is fully additive — no `DROP`, no `ALTER COLUMN TYPE`, no
constraint tightening. This satisfies the project-wide schema-lock rule
(documented in the schema itself: "schema-locked, additive-only") and is
required for `prisma migrate deploy` to be safe to run on a live database
without a maintenance window.

## Idempotency / safety properties

- `ReferralPayout @@unique([referralId, periodStart])` — the accrual scheduler
  can be re-run any number of times without double-paying. Enforced at the DB
  level, not just in application code.
- `Referral(referrerId) ON DELETE SET NULL` — removing a `Referrer` row
  preserves the legacy clinic-to-clinic `Referral` history. No cascade wipe.
- `ReferralPayout(referralId) ON DELETE RESTRICT` — you cannot delete a
  `Referral` that has payout history. This is the correct behavior for a
  financial ledger: a paid-out referral cannot vanish.
- `ReferralPayout(referrerId) ON DELETE RESTRICT` — same rationale: paid-out
  payouts must survive a referrer purge.
- New columns on `Referral` are nullable with no `DEFAULT`, so the `ADD
  COLUMN` runs without a table rewrite on existing rows.
- JSONB columns (`rateBands`, `creditConfig`, `payoutDetails`) have no CHECK
  constraints. Validation is enforced by Zod schemas in
  `referral-reward.rules.ts` (referenced by the `@json:` schema comments). The
  migration is intentionally permissive at the DB layer; the application
  layer is the source of truth for shape.

## Things deliberately NOT in the migration

- **No `@@unique` on `Referral.referredClinicId`.** Per item 2.6 of the
  deferred plan, this is held back pending an existing-data audit (legacy
  clinic-to-clinic referrals may have rows that would violate a one-per-clinic
  constraint). Do NOT add this constraint in a follow-up migration without
  first running the audit query and reconciling.
- **No backfill of `referrerId` on existing `Referral` rows.** The column
  starts NULL, and stays NULL for all clinic-to-clinic referrals (which is the
  intended semantic, per the schema comment). The new partner-referrer flow
  is opt-in: only new referrals created via the Referrer table will set
  `referrerId`.
- **No application-level enforcement of `Referrer.clinicId` consistency with
  `Clinic.id`.** The schema declares `clinicId String?` without a `@relation`,
  and the migration does the same. This is intentional: a Referrer is a
  *partner* (pharmacy, marketing person, custom), not necessarily a clinic —
  only `type = CLINIC` rows should have `clinicId` populated, and the
  application code is the place to enforce that invariant.

## How to apply

```bash
# 1. Stage & validate (no DB writes)
pnpm --filter @workspace/db exec prisma migrate diff \
  --from-schema-datamodel packages/db/prisma/schema.prisma \
  --to-schema-datasource packages/db/prisma/schema.prisma \
  --script

# 2. Apply against the target DB (staging first, then prod)
pnpm --filter @workspace/db exec prisma migrate deploy

# 3. Smoke test
pnpm --filter @workspace/db exec prisma validate
psql $DATABASE_URL -c "\d \"Referrer\""
psql $DATABASE_URL -c "\d \"ReferralPayout\""
psql $DATABASE_URL -c "\d \"Referral\""
```

The last three `psql` calls should show the new tables/columns exist with
the expected structure.

## Rollback

The migration is additive-only, so rollback is a SQL teardown of the new
objects. A reference rollback (for a no-traffic DB) is:

```sql
DROP TABLE IF EXISTS "ReferralPayout";
DROP TABLE IF EXISTS "Referrer";
DROP INDEX IF EXISTS "Referral_referrerId_idx";
ALTER TABLE "Referral" DROP COLUMN IF EXISTS "rewardClaimedAt";
ALTER TABLE "Referral" DROP COLUMN IF EXISTS "activationAt";
ALTER TABLE "Referral" DROP COLUMN IF EXISTS "referrerId";
DROP TYPE IF EXISTS "ReferralPayoutStatus";
DROP TYPE IF EXISTS "ReferrerRewardKind";
DROP TYPE IF EXISTS "ReferrerType";
```

This is not committed as a `down.sql` because the project's migration policy
treats additive migrations as one-way in production (see the schema-lock
comments). For dev/staging, `prisma migrate reset` re-runs from scratch.
